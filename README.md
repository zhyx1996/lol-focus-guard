# LOL 焦点守卫 · LolFocusGuard

[![build](https://github.com/zhyx1996/lol-focus-guard/actions/workflows/build.yml/badge.svg)](https://github.com/zhyx1996/lol-focus-guard/actions/workflows/build.yml)
[![license](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)
![platform](https://img.shields.io/badge/platform-Windows%207%2B-lightgrey.svg)

拦住「英雄联盟客户端 / WeGame 在后台时，自己蹦到前台抢焦点」的独立小工具。

- 单文件、单进程，**不注入客户端、不读内存、不改客户端文件、不装驱动**
- 只用公开的 Win32 窗口 API（`SetWinEventHook` 系列）
- 从"系统广播前台切换"到"窗口被收回、焦点还给你"，实测 **≈9ms**（一帧左右）
- .NET Framework 4.x + 系统自带 `csc.exe` 即可编译，不需要 SDK / Visual Studio

---

## 它解决什么问题

客户端在后台（最小化、或被别的窗口盖住）的时候，这些场景会突然抢走焦点：

- **匹配成功**、对局结束回到车库、排队/选人阶段的提示
- 客户端内部网页层弹的活动、赛事、公告页（`/riotclient/ux-show`）
- WeGame 把游戏拉起来时弹的「游戏进程已启动，等待游戏窗口拉起」卡片

只要不是你自己点的、不是 Alt+Tab 过去的，它就会在你操作的位置被打回去，
如果是"从最小化状态弹出来的"，还会顺手再最小化回去——不会在你面前杵一块客户端。

## 它做不到什么（先看这条，免得白装）

- **做不到"完全不出现"**。抢前台这个动作发生在客户端进程内部（`ShowWindow` +
  `SetForegroundWindow`），要在它发生**之前**掐掉，只能把代码塞进客户端进程
  （全局 `WH_CBT` 钩子 / API hook / DLL 注入）。那类做法会跟 ACE 反作弊直接冲突，
  本项目**不做**。物理上能做到的极限是"马上收回去"，也就是那 9ms 的闪现。
- 拦的是**窗口跳前台**这件事。客户端网页层的弹窗（活动浮窗之类）如果不产生独立窗口，
  本工具管不着——那是 Sona / Pengu Loader 这类 JS 层补丁的活。
- 全屏游戏里的表现要自己实测；EXCLUSIVE 全屏下系统的前台切换行为和非全屏不一样。

## 快速开始

1. 到 [Releases](../../releases) 下载 `LolFocusGuard.exe`；
2. 丢进任意文件夹，比如 `C:\Tools\LolFocusGuard\`（同目录可以放 `targets.txt`）；
3. 双击运行。托盘出现一个蓝色盾牌图标，开始工作；
4. 开机自启（可选）：`Win+R` → `shell:startup` → 把 `LolFocusGuard.exe` 的**快捷方式**丢进去。
   **建议在快捷方式的「目标」后面加 ` --verbose`**（例如 `"D:\Tools\LolFocusGuard\LolFocusGuard.exe" --verbose`）：
   普通模式只记"拦了谁、退出"，`--verbose` 才记"**为什么**放行/为什么拦、按住压了几次、切换器认没认出来"。
   真出问题时那几行就是全部证据，而实测 CPU 差别可以忽略（日志 8MB 自动轮转，不会无限涨）。
   改完自启项记得重启一次，或者用 `restart-guard.ps1`（它会用 WMI 起进程，脱离终端作业对象）。

> 单独一个 exe 就能跑；`targets.txt`、`lcu-dir.txt` 都是可选的配置文件。

## 配置

### `targets.txt` — 监控名单

默认：`LeagueClientUx`、`RiotClientServices`、`wegame`、`wegame_env`。
一行一个进程名（不带 `.exe`），`#` 开头是注释。改完**重启程序**生效。

命令行可以覆盖：`LolFocusGuard.exe --targets=LeagueClientUx,wegame`

### 命令行参数

| 参数 | 说明 |
|---|---|
| `--targets=a,b` | 覆盖监控名单（进程名，逗号分隔） |
| `--lcu-dir=<路径>` | 客户端安装目录（用来找 `lockfile`，只写日志，不参与判定） |
| `--no-click-allow` | 关掉所有「你在操作」的放行（测试用，等于什么都拦） |
| `--verbose` | 每次前台变化都写日志（含窗口类名/标题/尺寸/当次按键落在谁身上，排查问题用） |
| `--report` | 不开守卫，只把已有日志汇总成一份短报告（`%LOCALAPPDATA%\LolFocusGuard\report.txt`） |

出问题的时候这样取证，比发整份日志方便：

```powershell
.\LolFocusGuard.exe --report
notepad $env:LOCALAPPDATA\LolFocusGuard\report.txt
```

报告长这样：

```
时间范围: 2026-10-28 01:00:25 → 01:00:36
拦截: 5 次
  FakeClient / "FakeClient" ×5
放行: 21 次
  正在放弃拦截期 ×21
放弃拦截（防拉锯，10 秒内 5 次都没压回去才停手）: 1 次
判为自弹的依据:「350ms 内没有鼠标按键按下」5 次，「按键落在别的程序上」0 次
```

### `lcu-dir.txt` — 登录状态检测

一行客户端安装目录（里面应该有 `lockfile`），例如：

```
D:\WeGameApps\英雄联盟\LeagueClient
```

不写也行：程序会自己从客户端进程目录、`C:\Riot Games\League of Legends`、
`D:\WeGameApps\英雄联盟\LeagueClient` 里猜。

## 核心判据：区分「你自己切的」和「它自己弹的」

关键不是猜标题、也不是猜登录状态，而是**那一刻你有没有真的动鼠标**。判定依据是硬件级的两个事实：

- **鼠标按键是不是刚刚真的按下了** —— `GetAsyncKeyState(VK_LBUTTON/VK_RBUTTON)` 每 15ms 采一次，
  抓「按下」这一瞬间。它读的是硬件状态，**不是钩子**，ACE 掐不掉；
- **按下的那一刻指针落在谁身上** —— `GetCursorPos()` → `WindowFromPoint()` → `GetAncestor(GA_ROOT)` → 进程名。

| 情况 | 判定 |
|---|---|
| 最近 350ms 内**没有任何鼠标按键按下**，窗口却跑到前台了 | **拦截**（它自己弹的） |
| 按键按下，且那一刻指针在**被切到前台的这个窗口**上 | 放行（你点的） |
| 按键按下，且那一刻指针在**任务栏 / 任务栏缩略图预览 / 托盘溢出面板 / 开始菜单 / 任务视图**上 | 放行（你点的任务栏按钮/缩略图/托盘图标/开始菜单里的程序） |
| 按键按下，但落在**别的程序**上（你在打游戏、打字、点别处） | **拦截**（你点的是别的窗口，它没理由被抬起） |
| 1.5 秒内按过 `Alt` / `Win`（Alt+Tab、Win+数字、Win+D…） | 放行 |
| **Alt+Tab 切换器还开着**，或者**刚松手 2.5 秒内**窗口才画出来 | 放行（慢客户端从 Alt+Tab 过去 2 秒后才显示，1.5 秒的 Alt 宽限不够） |
| 上一个前台窗口**已经关闭**（刚打完这局、游戏窗口退出） | 放行（前台自然接管，不该"刚结束就被最小化"） |
| 排队的最小化动作**动手前会再复核一次**：这期间你点了**任务栏 / 任务栏缩略图 / 客户端窗口**，或按了 **Win+数字** | 放弃这次打回（说明你已经接管了；落在游戏画面/桌面/其它程序上的点击**不算**，照拦） |
| 刚**解锁 / 恢复会话**（2 秒内）：锁屏前客户端就在前台，Windows 把前台还给它 | 放行（系统行为，不是你让它弹的；超过 2 秒就恢复正常判定，不会白送免疫期） |

> **为什么"最近有没有输入"不够**：鼠标随手一动就算输入了。第一版就是拿「`GetLastInputInfo` 输入年龄 ≤ 500ms
> + 指针位置」判的，真机上被客户端将了一军：匹配成功弹到全屏时窗口正好盖在指针下面，
> 「指针在它上面」被当成「你点的」—— 一局 10 次弹窗全放行。改成「物理按键按下」之后，
> **鼠标只是躺着不动、或者只是划过去，都不再算数**：自弹没有按键，手动切一定有按键。
> （`test-cursor-covered.ps1` 专门复现"窗口盖住指针"这个场景。）
> 同理，**重试轮**（窗口赖在前台 1.2s 后再判一次）里指针必然压在它身上，所以那一轮
> 不把"指针在它上面"算成你点的。

再加一条**"刚放行过"的短期保护**（防「我刚点开你就给我最小化」），按两种情况分开给：

- **同一个窗口**：3 秒。你刚才就在用它，它内部又抢一次焦点不算它自弹（这条是"点不出来"的防线，别动）；
- **同一个程序（进程）的另一个窗口**：600ms，而且那个窗口**之前就见过**。
  原来这一档也是 3 秒，等于"你在客户端里点过任何一处，它 3 秒内自弹什么都放行"——
  「匹配成功」弹窗就是这么漏过去的。客户端**新造的窗口**连这条都不给。

这两条只放行、**不续期**：只有你真正动过的证据（点窗口、点任务栏、Alt+Tab、登录阶段）才会刷新保护期，
否则客户端每 2.x 秒自弹一次就能把保护期无限往后推。

再加一条**防拉锯阀**：判据是「我们**压不动**它」——每次拦截动作落地后都验收一次前台有没有真的离开它。
只有 10 秒内连续 5 次都没压回去（比如它是个一直往回抢的模态框），才放弃拦截 **15 秒**并记一笔日志；
压得下去的正常拦截一次都不计入，所以永远不会因为「拦得多」而自废防御。放弃期内每次仍然写一行日志，
免得你以为守卫没在跑。

> **为什么不拿键盘当放行理由**：打游戏时你一直在按 QWER，要是按键就算「你在操作」，
> 那客户端趁你操作时弹出来就永远拦不住了。所以键盘只认 `Alt`/`Win` 这两个「切窗口专用键」。
>
> **低级钩子（`WH_MOUSE_LL` / `WH_KEYBOARD_LL`）是"更快的那一路"，不是唯一一路**：钩子给的是
> 按下瞬间的事件，所以**极快单击（按下-抬起不到 15ms）也不会漏采**；判定用的三个字段
> （按下时间、按下时指针在谁身上、按下时指针下面的窗口类名）由钩子和 15ms 采样线程**写同一组字段**，
> 语义完全一致。但实测**WeGame 跑起来之后（它自带的 ACE / SGuard 安全模块）会把别的进程的低级
> 输入钩子悄悄掐掉**——钩子回调一次都不来，且不报错。所以钩子只是"更快"，采样线程才是保底：
> 钩子被掐掉时判定照样工作，最坏情况只是漏掉"比 15ms 还快"的那一下单击。
>
> 钩子回调跑在**输入线程**上，里面只做 `WindowFromPoint` + 类名/进程名查询，不写日志、不加锁、
> 不做耗时操作 —— 拖慢它等于拖慢整台机器的输入。

再加两条针对启动阶段的放行：

1. **客户端窗口第一次出现**（`LeagueClientUx` / `LeagueClient` / `RiotClientServices` 的窗口第一次冒出来）
   → 放行。登录页、启动页、安全检测都在这个阶段。收紧了两处：**一个客户端进程（pid）只放行一次**，
   而且要求这个进程**刚起来（< 120 秒）**——已经跑了几分钟的进程再冒出新窗口不可能是登录页，
   那就是它自己弹的（客户端每弹一次就新建一个 hwnd 的写法，原来每次都能白拿一次放行）。
   取不到进程启动时间（权限/反作弊）时退化为"只按 pid 一次"，宁可少拦一次也不能拦登录页。
2. **WeGame 登录阶段**：客户端进程还没起来时，`wegame.exe` / `wegame_env.exe` 的窗口一律放行。
   国服的账号登录/启动面板是 WeGame 弹的（窗口类 `TWINCONTROL`），拦了它你连"点击登录"都点不了。

> **WeGame 的窗口不一定属于 `wegame.exe`**：真机日志显示它的界面跑在
> `browser.exe`（窗口类 `CefTopWindow`、标题 `WeGame`）和 `pallas.exe`（窗口类 `TWINCONTROL`、
> `SIDE_WEB_VIEW`）里。只按进程名认目标，"游戏进程已启动"那张卡片、WeGame 的侧边网页
> 这些抢前台会整条漏过去。所以判据是**进程名 + 窗口标题/类名**一起看，
> 并且特意排除了 QQ 那个同名的 `browser.exe`（窗口类 `QBCoreAx`、无标题）。
> 这套分类是纯字符串比较，`LogicTest.exe` 里有 13 条对照用例。

> **为什么不按标题/类名判断**：登录页和登录后的客户端是**同一个窗口**——同一个 hwnd、
> 窗口类 `RCLIENT`、标题 `League of Legends`（客户端日志里 `Window 1` 从 `now visible`
> 到 `now restored` 一直是同一个，中途只换页面）。所以标题这条路走不通。
>
> **为什么不用"登录状态"判断**：本来打算读客户端本机接口（LCU，`lockfile` 里的端口+口令），
> 但实测腾讯版客户端的 `lockfile` **全程是 0 字节空文件**（登录前后都是），这条路作废。
> 现在代码里只剩一段只写日志的探测，不参与判定。


## 日志

`%LOCALAPPDATA%\LolFocusGuard\guard.log`，托盘右键 → 「打开日志」也能直接打开。

每条拦截长这样：

```
[2026-10-27 21:38:28.532] 拦截 #1：wegame (pid=26752) 自己弹到前台（刚才最小化=否，class=TWINCONTROL，
                          标题="WeGame"，尺寸=862x486@(422,266)，事件延迟=0ms）→ 打回
```

`事件延迟` 是"系统发出前台切换事件"到"我们收到"的毫秒数（正常 0–2ms）。

每局前后还会各留一行小结，方便对时间线（也顺便证明守卫一直在跑）：

```
[2026-10-29 20:21:03.933] 监测到客户端/WeGame 已启动：从现在开始盯前台（历史累计拦截 0 次）
[2026-10-29 20:21:19.479] 客户端/WeGame 已全部退出：本轮拦截 10 次（历史累计 10 次）
```

守卫连续运行每 30 分钟也会写一行 `仍在运行（已运行 N 分钟，累计拦截 M 次，客户端…）`，
所以"这局没拦"到底是不该拦、还是守卫半路退出了，看日志就能分清。

`LolFocusGuard.exe --report` 会把整份日志汇总成一份短报告（拦了多少次、都拦了谁、
放行原因分布、放弃拦截几次），排查时比自己翻日志快。

打完一局想知道「这次到底算不算达标」，直接跑：

```powershell
pwsh ./verify-real.ps1            # 读日志给结论：拦了谁、你有没有被误拦、哪里拦不干净
pwsh ./verify-real.ps1 -VerboseLog   # 如果那局是 --verbose 跑的，判定依据更全
```

它只读日志、不碰窗口，输出分「事实」和「判定」两段：事实是拦了多少次/都拦了谁/放行了哪些原因，
判定用 ✓ 表示这两个目标达成了（① 后台自弹被拦、② 你手动切窗口没被误拦），
用 ! 指出需要深挖的地方（放弃拦截 / 取消拦截 / 打回失败）。

## 已知局限

- **会有一次极短的闪现**，做不到完全不出现（原因见上）。打回后的"按住"（900ms 内反复压）
  能把"客户端顶回来—我们再压回去"之间的空档从 400ms 级压到 60ms 级，但第一次闪那一帧
  无法消除——外部程序只能在它抢到前台之后才反应。
  实测（无边框全屏窗口当量具、客户端每 80ms 抢一次）：按住 300ms 时游戏被打断 14 次、
  中位数 952ms；按住 900ms 后**被打断 0 次**。
- 如果你**主动**点客户端却被拦了（点击没被识别成"你点的"），再点一次即可，
  或者 `Ctrl+Alt+F9` 暂停。
- WeGame 的登录窗口和"游戏进程已启动"卡片同属 `wegame.exe` 那一套界面，
  目前靠"客户端进程起没起来"区分（登录阶段全放行）。极端时序下（卡片先弹、客户端后起）
  卡片可能被放行一次。
- EXCLUSIVE 全屏游戏下的观感需要在真打一局时确认。
- **Win11 的 `EVENT_SYSTEM_SWITCHSTART/SWITCHEND` 可能一次都不发**（本机就是：心跳里
  「切换器事件=0次」，可日志里明明有"任务切换"窗口）。这时 Alt+Tab 只能靠**窗口身份**认：
  `ForegroundStaging` / `MultitaskingViewFrame` / `TaskSwitcherWnd` /
  `XamlExplorerHostIslandWindow`（标题"任务切换"）。看见切换器就给你**下一次窗口激活一张
  一次性凭据**（`SwitchCredentialMs=2500`，用掉即失效）——不会像固定宽限那样留一段无防时间。
  日志里对应 `识别到任务切换器（…）` 和 `放行原因: 你刚用 Alt+Tab/任务视图切窗口（…凭据用掉了）`。
  手工验证：Alt+Tab 切到客户端，然后看日志有没有这两行。
  **另有键盘冗余通道**：15ms 采样线程发现「刚按下 Tab 且 Alt/Win 按着」时，也会打同一张凭据
  （日志 `识别到 Alt+Tab 按键（键盘采样）`）。两条路只要有一条命中就够——浮层没画出来、
  explorer 重启、两个全屏程序之间切换，键盘这条仍然有效。
  端到端回归：`test-switcher.ps1`（模拟"慢客户端"：Alt+Tab 后 1.9 秒目标窗口才上来，
  验证靠凭据放行、放行后不再打回）。
- **英雄联盟的窗口会挡掉别的进程的 `ShowWindow`**：实测它的登录窗口
  （`Client.exe` / `TWINCONTROL`）`ShowWindow(SW_MINIMIZE)` 直接返回 `False`、窗口纹丝不动，
  `SetWindowPos` 也一样；但它认 `WM_SYSCOMMAND / SC_MINIMIZE`——`PostMessage` 过去立刻最小化。
  拦下的动作里已经加了这条兜底（先 `ShowWindow`，验 `IsIconic` 没成功就换消息），
  日志里会写「ShowWindow 被挡，改用 WM_SYSCOMMAND/SC_MINIMIZE 最小化成功」。
- **偶发漏拦（该拦没拦）**：先看 `--verbose` 日志里有没有「取消拦截（请求 #N）」——
  那行会写清取消原因（排队期间你点了任务栏/客户端窗口、按了 Win、窗口已经不是前台、
  或者被更新的拦截请求取代了）。这条判据**认落点、只认 Win**：游戏里右键走位、
  点桌面、点聊天框、打游戏时的 `Alt`（自施法）都不会取消拦截。
- 没有可以交还的窗口时（比如上一个前台窗口本身也在监控名单里），光"不还焦点"等于没动作，
  所以这种情况直接最小化，由系统自己挑下一个前台窗口。
- **待验证：一局结束后客户端"自己回到前台"这件事会被当成自弹**。游戏进程（`League of Legends.exe`）
  退出后，客户端通常会自己顶到前台显示结算页；而守卫只认"你有没有点它"，所以这一步大概率被拦下
  （客户端被最小化，你得点一下任务栏才能看结算）。这**不是** bug 报告，而是**已知待办**：
  等一局真实对局结束时的 `--verbose` 日志确认了时序（客户端那次激活是不是紧跟在游戏进程退出之后），
  再决定要不要加一条"游戏刚结束 → 放行客户端这一次"的判据。
  **在那之前故意不动** —— 松一点就等于把"匹配成功抢前台"（本项目要解决的头号问题）又放回去了。

  > 探针已经装好了（`c5032f5`），日志里看这两类行：
  > - `观测: 游戏进程（League of Legends.exe）启动/退出`
  > - `拦截 #N：… → 打回（**距游戏进程退出 0.3 秒**）`（15 秒内才会带这个尾巴）
  >
  > 判读：客户端那次激活离游戏退出**零点几秒** → 就是结算页那条路，可以开口子；
  > 隔了几十秒 → 是别的东西在弹，**不能放**。这段纯观测，不参与任何判定。
- **带模态弹窗的窗口（"对局已就绪/接受对局"那种）只抢前台、不最小化**：这类窗口挂着模态
  对话框（`IsWindowEnabled=False`），最小化等于把它藏进任务栏，可能真的让你错过一局。
  现在的动作是：焦点照样不交给它，但**不最小化**——它留在后面、任务栏里还在，你想接受
  随时点任务栏或 Alt+Tab。日志会写 `这个窗口带着模态弹窗（…）→ 只抢回前台，不最小化`。
  只有在"没有窗口可以交还"时才仍然最小化（否则等于什么都没做）。
  回归：`FakeClient.exe modal`（自己 `EnableWindow(false)` 假装挂模态框）。
- **"按住"最多 900ms**：客户端（尤其"对局就绪"那一下）会在被打回后**几十毫秒内**把自己
  再顶回前台。只看重试间隔的话，这中间它就盖在你窗口上，观感仍是"强制跳前台"。
  所以打回之后动作线程就地按住 900ms：每 60ms 看一眼，它又占前台就再压一次
  （日志 `按住：它又抢了 N 次前台，都压回去了`）；一旦发现你在这段时间里点了鼠标、
  或打了 Alt+Tab 凭据，立刻收手（**进 sleep 前和醒来后各查一次**），绝不跟你抢。
  > 为什么从 300ms 提到 900ms：用无边框全屏窗口当量具实测，守卫自己记的「交还耗时」
  > 中位数只有 188ms（前台确实 200ms 内就还回去了），但**全屏窗口真正恢复渲染要 ~950ms**。
  > 按住只跑 300ms 时，剩下的 600ms 里客户端每次再抢，守卫都要重走一遍"事件→排队→
  > 最小化→交还"，游戏就一直拿不回来（实测被打断 14 次、中位数 952ms）。
  > 改 900ms 后同一测试：**被打断 0 次**（FakeGame 全程只在启动瞬间失去过一次前台），
  > 拦截次数反而从 31 降到 13 —— 按住期间它顶不回来，就不需要反复重新拦截。
- **「它自己就是最小化状态」的窗口**（真机 22:17 那种 `237x39@(-32000,-32000) 最小化=True`）：
  一律放行，不压回去（压回去只会打断客户端自己的"最小化→还原"链条，那正是"点好几遍才
  切出来"的来源）。但**不能就这么放着**：这种窗口不画任何像素，长期占着前台会让你
  屏幕上看得到自己的窗口、键盘却打不进任何东西。所以给它 400ms 宽限，
  还在原样占着就**只把前台交还给你、不最小化它**。日志 `复查: 最小化窗口占着前台超过 400ms…`。
- **打回失败后的重试间隔 120ms**（原来 400ms）。客户端顶回来的 400ms 里没人管，
  正是"匹配到对局时它还是跳出来"的直接原因。
- **「交还耗时」写进日志**：从"它抢到前台"到"前台已经不是它"一共多久（含判定排队、
  最小化、交还、按住）。这是你真正被打断的时长，`verify-real.ps1` 会直接给出中位数。
- **动作线程有卡死看门狗**：`AttachThreadInput` 会阻塞在目标线程的消息循环上。万一卡住，
  心跳照跳、日志照写，但**再也不会有任何拦截**，日志里一句错误都没有 —— 这是最难自查的
  失效模式。所以一个动作超过 3 秒没回来就记警告 + 补偿式再起一个动作线程。
  自测开关：`--selftest-action-stall`（往队列塞一个睡 10 秒的任务，3 秒后应报警）。
- **客户端刚起来 20 秒内不拦 WeGame 自己的窗口**：你用 WeGame 启动游戏时它把窗口递上来
  是启动流程的一部分，被缩掉纯属干扰。日志 `放行原因: WeGame 启动流程（…20000ms 内都算启动）`。
  这条只对 WeGame 家族生效，客户端自己的窗口照拦，20 秒后再自弹也照拦。
  回归：`test-rules.ps1` 阶段 2（宽限期内放行）+ 阶段 2b（宽限期过后必须拦），两个方向都锁住。

## 原理（技术细节）

**三层，按顺序**：

1. **事件**：`SetWinEventHook(EVENT_SYSTEM_FOREGROUND, WINEVENT_OUTOFCONTEXT)` ——
   系统级"前台窗口变了"的广播。回调里只判断、不做动作，耗时几十微秒。
2. **兜底**：独立线程每 50ms 读一次 `GetForegroundWindow()`，防止钩子漏事件。
3. **动作**（专用最高优先级线程，不占钩子线程）：如果是最小化状态弹出来的，
   `ShowWindow(SW_MINIMIZE)` 收回去；然后把前台交还给你原来的窗口
   （`AttachThreadInput` + `SetForegroundWindow`，不行再退一步 `SwitchToThisWindow`）。

**为什么这么快**：进程名用 `QueryFullProcessImageName` + pid 缓存（比
`Process.GetProcessById` 快一个数量级）；动作走专用线程而不是线程池；
最小化后只等 5ms 就检查前台是否已经交还。

**为什么不用注入**：全程只用公开的 Win32 窗口 API，不碰别人的进程空间、
不往客户端里装钩子。ACE 侧看不到任何异常行为。
